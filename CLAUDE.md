# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

**Build / compile**
```
sbt compile                 # or: sbt root/compile
```

**Dev stack** (backend + Scala.js watch + Vite, three panes)
```
npm run dev                 # concurrently: backend reStart, frontend fastLinkJS, vite dev
npm run dev:tmux            # same, in a tmux window (./dev-tmux.sh)
```
Vite serves the frontend at `:5173` and proxies `/api/*` to the backend at `:8080` (prefix kept as-is — backend routes are mounted under `/api`). Postgres must be up first: `docker compose up -d postgres` (copy `.env.example` to `.env` first). Naming the service matters now — a bare `docker compose up -d` builds and runs the whole deployment stack (see **Deployment**).

`.env` reaches the dev backend through `reStart / envVars` in `build.sbt` (the `dotEnv` helper), not through the shell — `sbt` has no notion of the file, so without that every `${?ENV_VAR}` override in `application.conf` silently kept its default under `~backend/reStart` while `docker compose` got the real value. It is a *setting*, so editing `.env` needs a `reload`, not just another `reStart`; a real shell variable still wins over the file. Most overrides default to something workable in dev, which is why this stayed hidden — the OAuth ones default to `""`, and an unconfigured provider is simply one the sign-in page offers no button for.

**Tests**
```
sbt test                                                        # everything
sbt backend/test                                                 # backend only
sbt "backend/testOnly webapp1.backend.service.AuthServiceSpec"   # single spec
sbt sharedJVM/test                                                # shared validation logic
sbt frontend/test                                                 # Laminar components, jsdom
npm --prefix web run typecheck                                    # frontend TS config only (no app TS)
```
Backend/shared specs run against a fresh, migrated SQLite DB per layer instantiation (see `TestDataSource.sqlite`) — no external services needed. The one exception:
```
docker compose up -d postgres
RUN_POSTGRES_TESTS=1 sbt backend/test    # PostgresIntegrationSpec, gated behind this env var
```
`PostgresIntegrationSpec` is the only place the Postgres dialect actually executes (testcontainers); everything else is Postgres-dialect-checked at compile time by Quill but runtime-tested on SQLite.

**E2E** (needs the full stack running — Postgres, backend, vite)
```
npm --prefix e2e install
npm --prefix e2e test
```

**Format**
```
sbt scalafmtAll
```

**Deployment** (`Dockerfile`, `docker-compose.yml`, `docker/`)
```
cp .env.example .env         # COMPOSE_PROFILES=db in it bundles Postgres
docker compose up -d --build # http://localhost:${HTTP_PORT:-8080}
```
Two images out of one multi-stage `Dockerfile`: `--target backend` (sbt-native-packager `backend/stage` on a JRE base) and `--target web` (nginx serving `web/dist`). **nginx, not the backend, serves the SPA** — the backend mounts only `/api`, so nginx also proxies `/api` through, keeping the SPA same-origin with the API; that is what the `X-Requested-With` CSRF check relies on in the absence of CORS. It is the only published port; the backend container is internal.

The frontend build stage needs a JDK *and* Node, because `vite build` shells out to `sbt frontend/fullLinkJSOutput` via `@scala-js/vite-plugin-scalajs`, and Tailwind scans `modules/frontend/src`. The whole repo is the build context.

Bundled vs. external Postgres is the `db` compose profile: with it (the `.env.example` default) `docker compose up` starts `postgres`; drop it and set `DB_URL` to reach a database you already run. The backend has no `depends_on: postgres` on purpose — a dependency on a profile-disabled service breaks `up` — so `restart: unless-stopped` plus its fail-fast Flyway startup covers the boot race.

Containers log to stdout via `docker/logback.xml` (`-Dlogback.configurationFile`), since the in-repo `logback.xml` writes to a relative `logs/` path. `APP_ENV` defaults to `dev` so the stack runs over plain HTTP out of the box; `APP_ENV=production` additionally requires `SESSION_COOKIE_SECURE=true`, an `https://` `PUBLIC_BASE_URL`, and a non-default `DB_PASSWORD`, or `AppConfig.productionIssues` refuses the boot — i.e. it assumes a TLS terminator in front of the `web` container.

## Architecture

Three-module sbt build: `modules/shared` (cross JVM/JS), `modules/backend` (ZIO HTTP), `modules/frontend` (Scala.js + Laminar + Waypoint), plus `web/` (Vite host for the frontend) and `e2e/` (Playwright). Full domain writeup is `summary.md`.

### Build-wide gotchas

- **`-noindent` is set in `commonSettings`** — significant-indentation Scala 3 syntax (`object Foo:`, colon+indent bodies, braceless `for`/`match`) does not compile. Every block needs explicit `{ }`, including `for { ... } yield`. This is easy to get wrong if writing "modern" Scala 3 style from habit.
- **`-Werror`, not `-Xfatal-warnings`** — the latter is deprecated in this Scala version and its own deprecation warning becomes fatal under itself, breaking every compile. Don't reintroduce it.
- `evictionErrorLevel := Level.Warn` is set deliberately: `quill-jdbc-zio` pins an older `zio-json` than the rest of the build uses directly; the eviction is safe, just don't remove the override without checking.

### Dual-dialect database strategy

Postgres is the only real target (see `docker-compose.yml`); SQLite exists solely so tests don't need Docker. Every repository is a plain interface in `backend/db/*Repository.scala`, backed by a single generic implementation (`*RepositoryLive[Dialect <: SqlIdiom, Naming <: NamingStrategy]`) that takes a `ZioJdbcContext[Dialect, Naming]` constructor param — the quoted-query bodies are written once. Interface, implementation and both `ZLayer`s live in one file per repository (`GroupRepository.scala` holds all four group-related ones); the `Repositories{,M2,M3}.scala` grab-bags they used to sit in are gone. `XRepository.live`/`XRepository.test` on the trait companion (next to its accessors) are thin `ZLayer`s that just supply a `PostgresZioJdbcContext`/`SqliteZioJdbcContext` instance to the same generic class — the SQLite one is named `test` because nothing but tests may wire it. Each repository method logs one INFO line through `QuillRepository.logged` (`<table>.<method>` plus ids and a row count / `found=` flag); **that message must never carry a password hash, session id, verification or invitation token, OAuth subject, or an email address** — the scaladoc on `logged` spells this out. Trade-off: because the dialect isn't statically known at the `quote` call site, every query compiles as a Quill "Dynamic Query" (rendered to SQL at runtime instead of baked in at compile time via the macro) — functionally fine (verified against real Postgres via `PostgresIntegrationSpec`) but gives up Quill's compile-time SQL generation/caching. Flyway migrations are still duplicated per dialect under `backend/src/main/resources/db/migration/{postgresql,sqlite}/`, kept schema-identical (all timestamps are epoch-millis `BIGINT`/`INTEGER`, not native timestamp types, specifically to keep the two dialects portable) — Flyway has no equivalent dialect-abstraction mechanism. `V4` is where the two diverge most: Postgres drops `users.google_subject` with a one-line `ALTER TABLE`, while SQLite refuses to drop a UNIQUE column at any version and has to rebuild the table (which is only safe because nothing enables `PRAGMA foreign_keys`, and the pragma is a no-op inside Flyway's transaction anyway — see the comment in the migration). `V6` rebuilds two more tables for the same reason (SQLite cannot alter a constraint), to match Postgres cascading `group_pairs.created_by` and `group_invitations.invited_by`. `V7` adds `login_attempts` and `audit_log`, the first two user references declared **`ON DELETE SET NULL` rather than `CASCADE`** — deleting an account must not erase the record of what was done to it or by it, which is why `audit_log.actor_email` is a denormalised snapshot rather than a join. `V8` adds `users.locale`, a plain `ADD COLUMN` on both dialects (one of the few `ALTER TABLE` forms SQLite supports, so no rebuild — unlike `V4` and `V6`).

**That pragma is a real blind spot: no foreign key is enforced on SQLite, so no cascade or constraint violation is exercised by anything except `PostgresIntegrationSpec`.** `AdminService.deleteUser` answered 500 for months for any user who had added a group pair — the two columns above were the only user references declared without an `ON DELETE` action — and the entire SQLite-backed suite passed throughout. Any change to referential integrity is only actually tested under `RUN_POSTGRES_TESTS=1`, and that is where its regression test belongs. `V7`'s two `SET NULL` columns are covered there for the same reason, in both directions: `CASCADE` would silently delete an account's audit trail along with the account, `NO ACTION` would bring back the 500, and SQLite passes either way.

`Main.scala` always wires the Postgres implementations. Tests wire the SQLite ones via `TestDataSource.sqlite`, a `ZLayer` that spins up a temp-file SQLite DB and runs the SQLite migrations, fresh per test.

### Backend request flow

**Every endpoint is described declaratively.** The API is stated once, in `shared`'s `api/*Endpoints.scala` (`Auth`/`Todo`/`Group`/`Invitation`/`Admin`), using zio-http's `Endpoint` API: paths, request/response bodies, and every status code, success and error. Three things are derived from those values, so none of them can drift from each other:

- `backend/http/*Routes.scala` supply handlers via `implementHandler`. A handler is a plain function from the endpoint's input type to its output type — no path pattern, no status, no JSON reading or writing, and no way to answer with a body the description doesn't allow.
- `backend/http/DocsRoutes.scala` generates one OpenAPI document from `<Resource>Endpoints.all` and serves it plus Swagger UI at `/api/docs/openapi` (public, mounted in `Main` — it exposes the shape of the API, not its data, and every endpoint it documents still needs whatever session the aspects demand). The session *is* documented, as an `apiKey`-in-cookie security scheme marked on every operation except the ones in `DocsRoutes.publicEndpoints` — that list is hand-maintained on purpose, because authentication is a `HandlerAspect` on a `Routes` value and nothing can read it back off the descriptions; `OpenApiSpec` pins the exact set on both sides so it cannot silently rot.
- `frontend/api/ApiClient.scala` and `AdminApiClient.scala` call them through an `EndpointExecutor` (`frontend/api/EndpointClient.scala`), so no page names a path or a method.

The two OAuth routes (`/api/auth/{provider}/start` and `/callback`) are the deliberate exception and the only ones still built as `Method / path -> handler`: both are top-level browser navigations whose success *and* every failure is a 302 into the SPA, so there is no body protocol to describe. They are consequently the only endpoints absent from the OpenAPI document, and (as before) the only ones exempt from the CSRF header. One pair serves every provider in `shared`'s `OAuthProvider`; an unknown *or* unconfigured segment answers the same 404. `GET /api/auth/providers` — which reports the configured ones so the sign-in form can render its buttons — is an ordinary described, public endpoint and is not part of that exception.

Every route file still exposes a `Routes[R, Response]` — an error channel of `Response` is what zio-http calls "handled". `Main.scala` concatenates all route files with `++`, then wraps the result in `RouteSupport.handleFailures`, which passes failure `Response`s through and turns defects (every `.orDie` in the services) into a logged cause plus a generic JSON 500. It also replaces `Routes.notFound` (a mutable field typed `Handler[Any, Nothing, Request, Response]`, and the only hook for it — assigning it does not affect the `Routes[Env, Nothing]` result, which comes from the `handleErrorRequestCauseZIO` above it): a request matching no route never reaches a handler, so zio-http would otherwise answer it with `Response.error(NotFound, path)` — the requested path echoed back, no JSON, no content type. **This 404 is not the one endpoints describe.** `ApiFailure.NotFound` means a resource the request named does not exist; this one means the path is not part of the API, so it is on no operation in the OpenAPI document and no generated client decodes it as a value — the client's URLs come from the descriptions, so it only arrives across a version skew between a deployed frontend and an older backend. Worth answering in the same shape as everything else for that narrow case, and worth not echoing the path back.

The cross-cutting checks are `HandlerAspect`s in `RouteSupport`, applied to whole `Routes` values with `@@` rather than called at the top of each handler:

- `csrf` — requires the `X-Requested-With` header, scoped with `.when` to methods outside GET/HEAD/OPTIONS.
- `authenticated` / `adminOnly` — `HandlerAspect[AuthService, User]`: they resolve the session cookie once and hand the `User` to the handler through the environment, so a protected handler reads `ZIO.service[User]` and cannot compile unless some aspect supplies it.
- `requestContext` — `HandlerAspect[AppConfig, RouteSupport.RequestContext]`: the client address (for rate limiting) and the raw session cookie (for logout). Neither is describable as an endpoint input — the address is not a header, and `Cookie` is a forbidden request header a browser sets itself — so they arrive through the environment the same way the `User` does. It needs `AppConfig` for `app.trusted-proxy-hops`, which is the *only* thing that makes `X-Forwarded-For` believable: `RouteSupport.clientAddress` ignores the header entirely at `0` (the default) and otherwise reads it **right to left**, taking the entry that many hops in, because each proxy appends and only the right-hand end is unforgeable. Both wrong answers are security bugs, and the second one shipped — with `0` behind the compose stack's nginx every request carried the proxy's address, and since `AuthService` blocks when *any* rate-limit key trips, five failed sign-ins from anybody locked sign-in, sign-up and verification resends for **every** account for as long as failures kept arriving. `RouteSupportSpec` pins each branch. `RateLimitKey.ip` keys IPv6 on the /64 (an address is free to change within one) and IPv4 on the exact address (aggregating would merge unrelated customers behind one NAT).

Aspects are attached last-runs-first (`routes @@ authenticated @@ csrf` checks CSRF before touching the session). Route files that mix public and protected endpoints (`AuthRoutes`, `InvitationRoutes`) build two `Routes` values and `++` them. **Never attach a context-providing aspect directly to a `handler` that also takes path parameters** — it hands the handler a bare `Request` where it expects the `(param, Request)` tuple, which compiles and then throws `ClassCastException` at request time. Put it on a `Routes` value.

One mapping per service failure enum lives in `backend/http/ApiFailures.scala` (`auth`/`todo`/`group`/`admin`), turning a `*Failure` into the `shared` `api.ApiFailure` case for the right status; route files call those rather than defining their own, so two endpoints that raise the same failure can't answer differently. Each returns the **union** of the cases it can produce (`todo` is `BadRequest | NotFound`), not `ApiFailure` — that is what ties the mappings to the descriptions, see below.

Six things to know before extending the API:

- **Each endpoint declares exactly the statuses a well-behaved caller can receive from it, and its error channel is the union of those.** Not one uniform set: `ApiEndpoint.failure` is the codec vocabulary and `.outErrors(...)` attaches a subset, e.g. `GET /api/me` declares only 401 while `PUT /api/groups/{id}/members/{userId}` declares five. The list is its handler's failures (whatever the `ApiFailures` mapper produces — nothing at all when the service call is a `UIO`) **plus 401 wherever `authenticated`/`adminOnly` guards it**, because a session expiring under a legitimately-open page is ordinary. That 401 bypasses the endpoint's codecs but a client built from the description still has to decode it, and a status a description omits is not decodable at all: the endpoint client fails it as a *defect* reading "Expected status code ... but found Unauthorized", so an expired session would otherwise reach the page as an unrenderable crash.
  - **Three statuses the server can still send are deliberately undescribed** — the aspects' 403 (`csrf` with no `X-Requested-With`, `adminOnly` for a non-administrator), 429, and 500. They are not answers to a well-formed request: the generated client always sends the CSRF header and no page routes a non-administrator to an admin call, and a defect is not part of the contract. `EndpointClient.run` flattens each into `ApiError(0, "Request failed: …")`, which is the right shape for them and would be the wrong one for a 401. The exceptions are all cases where the *service* raises the status rather than an aspect: the group and invitation endpoints declare 403 (`GroupFailure.NotMember`/`ReadOnlyMember`/`AdminOnly`, which `GroupMembersPage` renders), `POST /api/auth/login` declares 403 (`AuthFailure.EmailNotVerified`, which turns into a resend offer on the sign-in form), and signup/login/verification-resend declare 429 (`AuthFailure.RateLimited`, whose message the forms show). All of them are compile-forced — `ApiFailures.group`, `.auth`, `.authLogin` and `.resendVerification` produce those cases, so the endpoints have to declare them.
  - `outErrors[E]` takes `E` explicitly and only checks each codec is a subtype of it, so a union *wider* than its codec list compiles and then fails at encode time — nothing catches that; keep the two in step by hand. In the other direction it is sound: a handler that fails with `ApiFailure.Conflict` on an endpoint that doesn't declare 409 does not compile.
  - `outErrors`' smallest overload takes **two** codecs, and several endpoints are now down to one (just the 401). `ApiEndpoint.outFailure` installs a single one the same way `Endpoint.outError` does, so the status stays named only in `ApiEndpoint.failure`. `POST /api/auth/logout` declares no failure at all and so calls neither.
  - `OpenApiSpec` pins the whole per-operation status table (136 declared failure statuses across 44 operations; it was 135 before `GET /api/admin/users` grew paging query parameters and with them a `codecError` 400, 133 across 43 before `PUT /api/me/locale`, 100 across 31 before the administrator diagnostics, 96 across 29 before email verification, 90 across 25 before the account-settings endpoints, down from 126 when the aspects' statuses were described and 175 under the uniform set), plus the rule itself — 403 only on group/invitation paths and login, 429 only on signup/login/verification-resend, 500 nowhere. `ApiEndpointsSpec` pins that the aspect-built bodies, described or not, are still `ApiFailure`-shaped on the wire.
  - Residual slack: the ten group endpoints all declare the same five because every `GroupService` method is typed `IO[GroupFailure, ?]` and the mapper covers 400/403/404/409, even though e.g. `getGroup` cannot raise a 409. Tightening that means narrowing the service signatures, not the descriptions.
- **`outErrors` is only half the error story — `codecError` is the other half.** An `Endpoint` carries two error codecs. `outErrors` describes what the *handler* raises; `codecError` covers what fails before the handler is ever called — a body that does not parse, a wrong `Content-Type`, a header or query codec that does not decode. `Endpoint.implementHandler` catches that `HttpCodecError` itself, so it reaches neither `ApiFailures` nor `handleFailures` nor `JsonSupport`, and its status is fixed at 400 by the library. Left at the library default it answers a private `{"name":"MalformedBody","message":"…"}` shape, offered as `text/html` ahead of `application/json` — not `dto.ErrorResponse`, and nothing a generated client decodes. `ApiEndpoint.withCodecError` routes it through `ApiFailure.BadRequest("Malformed request")` instead, and is applied to every endpoint with an input. It **replaces** the field rather than going through `Endpoint.outCodecError`, which would combine as `codec | self.codecError` and hand an `Accept: text/html` caller back to the HTML default.
  - Two consequences when adding an endpoint: apply `.withCodecError` if it has an input, a query parameter or a header codec, and declare `failure.badRequest` even if its handler cannot fail — that is why `PUT /api/me/theme` declares a 400 despite an `.orDie`'d service call. Without the declaration the 400 matches neither the output nor the errors and the client turns it into a defect.
  - The discarded `HttpCodecError` is not logged anywhere: the transform is a pure function and zio-http offers no effectful hook at that point.
- **Only `ApiFailure.BadRequest` carries `fieldErrors`.** It's the only failure attributable to individual form inputs and the only one any mapping ever filled in; the other six used to carry an always-empty `Map` because the sealed trait demanded it. The trait declares `error` and `message`. Wire effect: a 409 is `{"error":{...},"message":...}` with no `fieldErrors` key, which still decodes as `dto.ErrorResponse` (whose field defaults to empty). The duplicate-email 409 consequently lost its `"email" -> ...` entry — nothing in the frontend read it (no page reads `ApiError.fieldErrors` at all today; they render `err.message`).
  - **`error` is a `MessageRef`, and it is the half the SPA actually renders**; `message` is the English fallback for callers with no catalog. See **Internationalization** below — `fieldErrors` is consequently `Map[String, MessageRef]`, not `Map[String, String]`.
- **`.out[Unit](Status.NoContent)` does not work for a browser client**; every 204 (`deleteUser`, `logout`, four group endpoints) uses `.outCodec(HttpCodec.status(Status.NoContent))` instead. Both put an empty 204 on the wire, but `out[Unit]` installs a body codec that needs to know the body is empty, and zio-http's Scala.js `FetchBodyInternal.isEmpty` only reports empty when `Content-Length: 0` is present — which a 204 must not send (RFC 9110 §8.6). The scaladoc on `AdminEndpoints.deleteUser` records this.
- **The session `Set-Cookie` is described, but optional** (`ApiEndpoint.sessionCookie`, used by signup/login/logout). `Set-Cookie` is a forbidden *response* header: the browser applies it and then hides it from `fetch`, so a required header codec would fail to decode every successful login. Optional makes it a `None` the page ignores, while the JVM client (`AuthFlowSpec`) still sees the real value and the OpenAPI document still records that these endpoints set a cookie.
- **Two codec stacks.** The `Endpoint` codecs are zio-schema (instances in `api/ApiSchemas.scala`), *not* the zio-json codecs the DTOs derive and `dto.ErrorResponse` still uses in `JsonSupport`. That they agree is a fact pinned by `ApiEndpointsSpec` on real bytes, not a guarantee (they do agree today, including `Theme`/`TodoStatus`/`GroupRole` as bare strings; the only difference is that an empty `fieldErrors` map is omitted instead of written as `{}`).
- **Bundle cost.** `shared` carries `zio-http` + `zio-schema-derivation` on **both** platforms. Measured with `fullLinkJS`: 471 KB gzipped before any of this, 585 KB with the dependencies merely present (almost all of it the `scala-java-time-tzdb` blob they drag in), 1.28 MB now that the ZIO runtime links in and every page's calls go through it. Note the marginal cost of the non-admin endpoints was *negative* — 1.33 MB when only the admin pages were generated — because retiring the hand-written `fetch` client took the zio-json decode paths for those DTOs with it. To get the whole 800 KB back, the declarative frontend path has to go: move `api/*Endpoints.scala` + `api/ApiFailure.scala` + `api/ApiSchemas.scala` to `modules/shared/jvm/src/main/scala`, scope the dependencies with `.jvmSettings`, and hand-write the frontend clients again.

Session auth is a random opaque token in an `HttpOnly`/`SameSite=Lax` cookie (`SessionAuth`), not JWT. CSRF is mitigated by requiring a custom header on mutating requests (cross-site requests can't set one without a CORS preflight) rather than a token scheme — the OAuth callback is the one exception, since it's a top-level browser redirect that can't carry custom headers; it's protected by the `oauth_state` cookie/query-param match instead. That cookie holds `nonce|intent|locale` while the echoed `state` parameter holds only the nonce, so the halves deciding whether the callback signs in or links a provider, and which language's page it redirects back into, never leave the `HttpOnly` cookie jar. The outbound calls go through zio-http's `Client` — hence `Client.default` in `Main`'s layers and in the specs that build `OAuthClients.live` — not `java.net.http`: a synchronous `send` inside `attemptBlocking` is uninterruptible, so a provider endpoint that stalls after connecting used to pin a blocking-pool thread until the OS gave up on the socket. There is deliberately **no CORS middleware**: the SPA is same-origin with the API (Vite proxies `/api` in dev, a reverse proxy in production), and enabling CORS would be what lets a cross-site page preflight its way past the `X-Requested-With` CSRF check.

### Social sign-in and account linking

External identities live in `oauth_identities(provider, subject, user_id)` (unique on `(provider, subject)`), not in a column on `users` — `google_subject` was dropped in `V4`. **`(provider, subject)` is the only thing that may decide which account a social sign-in enters.** When it misses and the email is already taken, `AuthService.loginWithOAuth` **fails** with `OAuthAccountExists` rather than logging into the existing account: any provider that lets a user assert an address they don't control would otherwise be an account-takeover path, and `email_verified` doesn't generalise across providers (Microsoft asserts no such claim at all). The stored `email` is display metadata only. The recovery route is to sign in normally and link from `/settings`, which is why that page is a hard dependency of this rule and not a nicety.

`AuthService.unlinkOAuth` refuses to remove an account's last credential (`LastCredential` → 409) — without it a social-only account can lock itself out irrecoverably in one click. `SettingsPage` disables the button too, but the server check is the real one.

Providers are `OAuthClient` implementations behind `OAuthClients.forProvider`, which returns `None` for anything unconfigured; adding one is a config section plus one class. Google verifies its `id_token` via the `tokeninfo` endpoint. **Microsoft has no such endpoint**, and rather than take a JWT/JWKS dependency, `MicrosoftOAuthClient` base64url-decodes the payload and validates `iss`/`aud`/`exp` as ordinary fields — which OIDC Core 1.0 §3.1.3.7 item 6 permits *only* because the token arrives over a direct back-channel TLS call to the token endpoint. `decodeIdTokenClaims` must never be reused on a token that reached the server any other way; that one would need a real signature check. `MicrosoftOAuthClientSpec` pins each claim check.

Config moved from a top-level `google` section to `oauth.{google,microsoft}` (`AppConfig.isOAuthConfigured`, `configuredOAuthProviders`); `MICROSOFT_TENANT` defaults to `common`, admitting work/school and personal accounts alike.

### Email verification

`users.email_verified_at` (`V5`, backfilled from `created_at` so no existing account is locked out) plus single-use tokens in `email_verification_tokens`, issued by `AuthService.signup` and `resendVerification` and redeemed by `verifyEmail`. Tokens are 32 `SecureRandom` bytes stored in plaintext, same as session ids and group invite tokens; they last 24 hours and `SessionReaper` prunes the expired ones alongside sessions.

**The tokens are always issued and always redeemable; `app.require-email-verification` (default `false`) only decides whether an unverified account may *log in*.** With it on, `signup` returns no session — hence `SignupResponse(user, signedIn)` rather than `AuthResponse`, since a missing `Set-Cookie` is invisible to `fetch` — and `login` fails `EmailNotVerified` **after** the password check, so the gate is not an account-enumeration oracle. That failure is the API's one 403 outside `/api/groups` and `/api/invitations`, and it gets its own `ApiFailures.authLogin` mapper: widening `ApiFailures.auth`'s union would force a 403 onto signup, unlink and set-password too.

`POST /api/auth/verification/resend` answers 204 for an unknown address, a verified one and a fresh send alike — the copy on every page that calls it must stay as non-committal as the endpoint — with its own `RateLimitKey.verification` namespace so resends and logins don't share a budget. OAuth-created accounts start verified only when the provider asserts `email_verified` (Google does, Microsoft never), and `linkOAuth` verifies an account when the provider vouches for the *same* address. Admin-created accounts and the bootstrap admin are inserted verified.

Mail goes through `EmailSender`, now `RLayer[AppConfig, EmailSender]`: `SmtpEmailSender` (Jakarta Mail, via `angus-mail`) when `mail.smtp.host` is set, `LoggingEmailSender` otherwise — the same "empty string switches it off" idiom as the OAuth providers, and the reason a dev stack boots with no mail server. `AppConfig.productionIssues` refuses to start on `APP_ENV=production` + verification required + no SMTP host. Tests use `RecordingEmailSender`/`SentEmails` (`TestAuthLayers.scala`), which is the only way to get at a token — deliberately, and why the e2e suite covers none of this.

### Administrator diagnostics, audit trail and system overview

The admin surface answers *about* accounts, never out of them. `AdminService.userDetail` is the one endpoint behind the account screen's four diagnostic cards, and four things the server holds are projected away before anything leaves it: the password hash, the OAuth `subject`, the verification token, and **the session id — `dto.AdminSessionInfo` carries no identifier at all, not even a prefix, because the `sessions` primary key *is* the bearer token.** That is why session revocation is per account (`DELETE /api/admin/users/{id}/sessions`) and there is no per-session form of it. `ConfigSummary` follows the same rule for the deployment: every credential-bearing setting is a boolean or absent, `db.url` has any userinfo stripped by `SystemService.redactUrl`, and `SystemServiceSpec` asserts it against the serialised bytes and the *field names*, not against a remembered list.

Two persistent tables back it, and both are read-only from the API's point of view:

- **`login_attempts`** — every sign-in outcome, written by `AuthService.login` at all six of its exits (`dto.LoginOutcome`'s vocabulary, plain strings so a row written by an older build still renders). The in-memory `RateLimiter` is still the enforcement and still knows only the current 15-minute window; this is the history. **The write is `catchAllCause`'d** — recording an attempt is observability, and a dead table must never turn a correct password into a failed sign-in.
- **`audit_log`** — every administrator action, written by `AuditTrail.record`, which is also the one place that emits the `SecurityLog` line. One method for both on purpose: the log and the screen would otherwise describe different sets of events. The write is likewise swallowed on failure, since the log line has already gone out and a 500 would tell the administrator the action did not happen.

`AdminActor(userId, clientIp)` replaced the bare acting-admin id so the audit row can say where an action came from; `AdminRoutes` is consequently the one route set carrying **two** context-providing aspects (`adminOnly` for the `User`, `requestContext` for the peer address). Both are on the `Routes` value, never on a `handler` — see the warning above about what that does to a handler with path parameters. `RouteGuardsSpec` drives a mutating admin route with a path parameter through the real stack, because getting it wrong is a `ClassCastException` at request time rather than a compile error.

**Each authentication path has its own `RateLimitKey` namespace, and that is a correctness rule, not tidiness.** `email:`/`ip:` for login, `verify:` for verification resends, `signup:` for signup. Signup counts a *duplicate address* as a failure and the address is the caller's to choose, so while it shared `email:` with login, five signup attempts against a known address locked its owner out of signing in — an unauthenticated account lockout costing the attacker nothing but the address. `AuthServiceSpec` pins both directions. Note `AdminService.lockoutKeysFor` deliberately does **not** include the signup key: it answers "what is keeping this account out", and a signup budget no longer keeps anybody out.

`RateLimiter` gained `status`/`snapshot`/`clearAll`/`pruneStale` so the lock is inspectable and clearable; `AdminService.clearLockout` clears the address key, the verification key **and** every `ip:` key the account was recently attempted from (`login_attempts.distinctRecentIps`) — `login` blocks if *any* dimension trips, so clearing one leaves the user locked out. `SystemService.prune` calls `pruneStale`, not `clearAll`: housekeeping must not quietly unblock an account that is being brute-forced.

`BackgroundJobs` is a `Ref` the two daemon loops (`SessionReaper`, the rate-limit pruner) report each pass to. Without it a `.forever` loop that has died looks exactly like one with nothing to do, and the system overview would be showing a hard-coded "running".

`SessionReaper.sweep` removes three things, not two: expired sessions, spent verification tokens, and `login_attempts` rows older than `app.login-attempt-retention-days` (30). That third one is the only table an unauthenticated caller can grow at will — `AuthService.login` writes a row at *every* exit, including the one the rate limiter takes before checking a password — and nothing swept it, so `LoginAttemptRepository.deleteOlderThan` sat unused while the table grew forever and two of the system overview's `COUNT(*)`s grew with it. `audit_log` is deliberately **not** swept: how long to keep the record of administrator action is the operator's call, not a default.

`SystemService` memoises `DbStats` for `statsCacheTtl` (30s) because one overview is ~15 `COUNT(*)` queries; the config summary and the runtime figures stay live, since a memoised heap reading would be worse than none. **`prune` clears the memo** — without that the administrator's maintenance button appears to do nothing, and `SystemServiceSpec` asserts it.

**Test gotcha:** `Request.get("/path?a=b")` does *not* parse a query string — the whole string becomes the path, the request matches no route, and the answer is `handleFailures`' 404, which looks exactly like a broken endpoint. Use `RouteRunner.getWithQuery`.

**No bearer credential may appear in a log line, and that includes the URL.** `QuillRepository.logged` states the rule for repositories, but the request log broke it independently: `Middleware.requestLogging()` writes the whole URL, and two of this API's credentials travel inside one — the group invitation token is a path segment (`/api/invitations/{token}`) and the OAuth authorization code is `?code=`. `Main` therefore uses `RouteSupport.withRequestLogging`, which logs the path only (never the query string), replaces the invitation token with `…`, and keeps the same four annotation keys (`method`, `url`, `status_code`, `duration_ms`) that `logback.xml`'s `%kvp` rendering expects. nginx writes `$request` verbatim and had to be told separately — hence the two `access_log off` locations in `docker/nginx.conf`. Every opaque token in the application now comes from `security/Tokens.scala`; **`zio.Random` is not an alternative**, since its live implementation is `scala.util.Random`, a 48-bit LCG, and the OAuth `state` nonce was generated with `Random.nextUUID` — predictable to anyone who could sample a few, on the one route that cannot require the CSRF header.

Security-relevant events (failed logins, rate-limit trips, admin-route denials, admin user-management actions) go through a dedicated slf4j logger named `"security"` (see `logback.xml`), separate from general app logging. They are emitted via `security/SecurityLog.scala` (`SecurityLog.warn` / `.info`) — grep for `SecurityLog.` to find all call sites. That object logs through ZIO (so the lines carry fiber id and log annotations) and steers the SLF4J backend at the `security` logger with zio-logging's `loggerName` aspect; don't reintroduce direct `LoggerFactory.getLogger` calls. Administrator actions additionally land in `audit_log`, always through `AuditTrail`.

Config (`AppConfig`) is HOCON (`application.conf`) with `${?ENV_VAR}` overrides, loaded via zio-config + zio-config-magnolia; field names are camelCase, config keys kebab-case (`.kebabCase` provider transform bridges them). `.env.example` documents every override. `AppConfig.provider` is *installed* as the config provider (`AppConfig.configProvider` = `Runtime.setConfigProvider`), not just read through — it's in `Main.bootstrap` alongside the SLF4J layer, and `AppConfig.live` (`configProvider >>> ZLayer(ZIO.config(configDesc))`) composes it in itself so the layer stays self-sufficient in tests, which have their own bootstrap. Without that, a `ZIO.config` call anywhere else would silently fall back to env vars and system properties.

The server is wired with `Server.customized`, which needs both a `Server.Config` (`.binding(app.server-host, app.server-port)`) and a `NettyConfig` (`.maxThreads(netty.max-threads)`; `0` means "let Netty decide", i.e. 2× cores) — both derived from `AppConfig`, so there's one source of truth for host/port and no `Server.live`/`defaultWithPort` shortcut.

### Paged, sorted and filtered listings

The two long admin listings — `GET /api/admin/users` and `GET /api/admin/audit` — are paged, ordered and narrowed **by the database**, and both answer a `{items, total}` body (`dto.UserPage`/`dto.AuditPage`) rather than a bare list. The `total` is what makes numbered pages possible at all: it counts what the *filter* matches, not what the table holds, and the page buttons are arithmetic on it.

`dto.Paging` in `shared` is the single source of the policy — `firstPage` (1), `defaultPageSize` (20), the `pageSizes` the dropdown offers (20/50/100), `maxPageSize` (the largest of those), and `pageCount`. Both ends read it: the browser draws its buttons off `pageCount` while `AdminRoutes` turns `page`/`pageSize` into the SQL `OFFSET`/`LIMIT`, so the dropdown cannot offer a size the server would clamp. **The cap is the protection, not tidiness** — `pageSize` reaches the `LIMIT` directly. A page number is floored at the first page but deliberately *not* clamped at the top: the server has not counted anything when it reads the parameter, and an empty page with an honest total is what lets the browser correct itself (`Pagination.clampPage` on read, so no page writes a corrected number back).

**Pages are numbered from one, everywhere.** `?page=2` is the second page in the address bar, in the request, in `UserQuery.page` and on the button; `Paging.offset` is the only place the number becomes rows to skip, and `Paging.firstPage` is the only place the number `1` is written down. It used to be a zero-based index all the way out to the URL, which meant the second page was `page=1` — a detail no reader of the address bar has any reason to expect. `?page=0` is consequently not an error but the first page, since there is no page zero to answer with.

**The audit trail was cursor-paged (`before=<oldest occurredAt shown>`) and is not any more.** A cursor is the stabler of the two under concurrent writes — an offset shifts when a row is inserted above the page being read — but it can only walk backwards from where the reader already is: it cannot number pages, cannot jump, and has nothing to count a total against. That is what the change cost, and it is recorded on `AdminEndpoints.auditLog`.

Ordering is three-state per column (`components/SortHeader`): unsorted → ascending → descending → unsorted. The third state is the one that matters — without it there is no way back to the listing's own order, which for the audit trail is "most recent first". The wire vocabulary is `dto.UserSort`/`dto.AuditSort` plus `dto.SortDirection`, all plain strings, and **an unrecognised `sort` is not an error**: the repository's `ordered` falls through to the listing's default, so a client may stop sending a sort without coordinating a deploy. The mapping from a column name to an `ORDER BY` lives in the repository, since that is the only layer that knows a column exists; `QuillRepository.ordering` picks `Ord.asc`/`Ord.desc` at runtime and has to be passed with `using`, because Quill's own `implicitOrd` would otherwise silently supply `ascNullsFirst`.

Two columns are deliberately unsortable. The user list's sign-in column is a badge joined in from the rate limiter's process-local `Ref`, so there is no `ORDER BY` that could produce it; the audit trail's target is two fields rendered as one. Sorting on a nullable column (`emailVerifiedAt`, `actorEmail`, `ip`) leaves the nulls wherever the dialect puts them — neither dialect is asked and neither answer is wrong.

The user list's search box is `q=`, a case-insensitive substring of the address. It is case-insensitive **because addresses are stored lowercased** and the needle is lowercased to match — there is no `lower()` in the SQL for the two dialects to disagree about. A `%` or `_` typed into the box is still a wildcard; escaping them needs an `ESCAPE` clause the dialects spell differently, and a wider match is a harmless answer to a rare input. The term is debounced in the browser (300ms) rather than throttled on the server, and **it never reaches a log line** — it is a fragment of somebody's address, which `QuillRepository.logged` forbids like any other.

Each listing holds its whole request in one case class (`frontend/listing/UserQuery`/`AuditQuery`) rather than four `Var`s, because the parts are not independent: narrowing the search or reordering the table invalidates the page index, and holding them apart means every writer has to remember to reset it (`reset` is that rule, and every writer but "turn the page" goes through it). Being a case class it compares by value, which is what lets `.distinct` turn "something changed" into "ask the server again" — and why each page also carries a `reloadBus`, for the case where the answer should be re-fetched without the question changing.

**That case class is the argument of a route, not a page-local `Var` — the URL is where the listing state lives.** `/en/admin/users?page=2&sort=email&dir=desc&q=bob` is the whole thing, so a filtered view can be bookmarked, sent to a colleague, and walked back through with the browser's back button. `AdminUsersPage`/`AdminAuditPage` consequently take a `Signal[Query]` and an `Observer[Query]` and own none of it; `App` supplies the pair. **It writes with `pushState`, so the back button steps back through the listing** — a page turn, a column, a page size and a filter are each somewhere a reader can want to return to. The one exception is a search term being typed out further (`UserQuery.refines`), which `replaceState`s, so one search costs one history entry however long the term is and the back button leaves the search rather than walking through its letters. A write that changes nothing (the audit page's Apply button re-asking for the listing it already shows) does not touch the history at all — that is a reload, not a navigation. Every listing change used to replace, which is why the back button left the screen with the first press. The four parameters every listing has — `page`, `size`, `sort`, `dir` — are `listing/ListingParams`, so a third listing is its own case class, its own extra parameters, and one route. Five things follow, and each of them is a bug if it is got wrong:

- **`App` renders the two listings through `SplitRender.collectSignalPF`, not `child <-- signal.map(render)`.** With the query inside `Page`, every keystroke is a new `Page` value, and the ordinary path would rebuild the page element on each one — discarding the search box's focus, the loaded rows and the in-flight request. Waypoint's signal renderer builds the element once and feeds it the query (`CollectPageSignalRenderer` holds a `Var` and `discard()`s it when another renderer takes over). The catch-all `collectStaticPF` re-runs on every emission, which is why `viewSignal` keeps its `.distinct`.
- **Each listing has *two* routes, query first.** url-dsl's `createUrlString` joins path and parameters with `?` whether or not there are any parameters, so a single `Route.onlyQuery` would address the plain list as `/admin/users?`. The query route is a `Route.onlyQueryPF` defined — in both directions — only for a non-default query; the bare path is a `Route.staticPartial`. The router takes the first route that answers and uses the same list for building a URL and for matching one, so the order is load-bearing in both directions.
- **The history tag carries the query too** (`AppRouter.serialize`/`deserialize`). Waypoint restores a page from `deserializePage(history.state)`, *not* by matching the URL again, so a tag that dropped the query would answer the back button with the filter silently gone. Both reuse the same `QueryParameters` value the URL is built from, so there is one encoding rather than two — and a search term containing `&` or `=` survives it.
- **A hand-edited URL is bounded, not refused.** `pageSize` reaches the SQL `LIMIT`, so the decode clamps it with the same `dto.Paging` helpers the server uses; an unknown `sort` column is dropped rather than kept, because the server would order by its own default anyway and a sort in the address that no heading marks is worse than none.
- **The search box follows the query, and never the other way round: what reaches the query is the `onInput` *stream*, not the box's `Var`.** The box has to follow the query — that is what puts `?q=bob` from a bookmark into it, and what the back button restores — and reading it back to decide whether the reader had cleared it is what made `/admin/users?q=bob` open unfiltered. A `Var` write opens an Airstream transaction, and a transaction opened inside a running one is *queued*; the page mounts inside one (`App`'s gate opens on a `Var` write), so at that instant the box still held `""` while the query said `bob`. The debounce compared the two, concluded the box had been cleared, and `reset` the query — clearing the filter and the page number with it. A stream has no value to compare on mount, so nothing at all is asked for until somebody types. `AdminUsersPageSpec.withPageMountedInTransaction` mounts through a `child <--` switch for exactly this reason; the plain `L.render` helper next to it runs outside any transaction and cannot see the fault.

`Page.Admin` and `Page.AdminAudit` are case classes as a result, so `AdminSubmenu` matches them by type rather than by `==`: a tab that went dark as soon as somebody sorted a column would be answering the wrong question. `AppShell` and the submenu link to `Page.Admin()` — the default view, i.e. the clean path. `AdminUserDetailPage`'s "back to users" link does the same, and so loses the listing the reader came from; carrying it would mean `Page.AdminUserDetail` holding a `UserQuery` of its own.

### Internationalization

English and Hungarian, across the whole stack. Adding a third language is `Locale`'s enum, a `messages.<code>.json`, and the `plural` match in `MessageCatalog`; `MessagesSpec` then fails until the new catalog has every key.

**The URL decides the language.** Every SPA route is served under a prefix — `/en/groups`, `/hu/groups` — and that is the *only* thing that decides what a page renders in. Waypoint does the work: `basePath` is a defaulted parameter on every `Route` constructor, prepended when a URL is built (`relativeUrlForPage` is `basePath + createRelativeUrl(args)`) and stripped when one is matched, so `AppRouter` passes `CurrentLocale.prefix` to each route and `Page` is untouched — no locale field, no new serialization tag, no changed call site. Three consequences worth knowing:

- **The locale is known synchronously, before anything mounts** (`CurrentLocale.fromPath` reads `location.pathname`). So `Main` fetches the catalog *before* `render`, and `I18n.t` is an ordinary synchronous function. There is no `localeSignal`, no `text <--` binding for static copy, and `App`'s deliberately narrow render `Gate` did not have to widen.
- **Switching language is a full page navigation**, not a re-render — `LanguagePicker` is plain anchors to the same path under the other prefix, inside a popover dropdown. A route's `basePath` is fixed when the router is built, so the document has to reload; that reload is also what fetches the new catalog. The trigger shows the current language's code (`EN`, `HU`) and the menu spells each one out (`HU - Magyar`); both halves follow the endonym rule and neither is translated. The entries are only clickable once the dropdown is open, which is what the picker's e2e test has to do first.
- `web/index.html` carries a small inline boot script that puts a prefix on a prefix-less URL before the bundle loads, and sets `<html lang>`. Deliberately there rather than in nginx or Vite, so dev and production behave identically and `navigator.languages` is reachable.

**Precedence, and the one rule that is easy to get backwards:**

```
explicit URL prefix  >  stored users.locale  >  localStorage  >  navigator.language  >  en
```

A stored preference must **never** override a prefix the visitor actually opened — deliberately opening `/en/groups`, signing in and being thrown to `/hu/groups` is a bug. So the account's language only decides anything when the URL had no prefix and the boot script had to guess, which it records in `sessionStorage` as `localeImplicit`. When the URL *was* explicit and disagrees, the URL wins and is written back as the new preference. The rule is `LocaleSync.decide`, a pure function, and `LocaleSyncSpec` states it as a table.

`users.locale` (`V8`) exists for two things the URL cannot reach: **transactional email**, composed server-side with no browser in the room, and seeding that first prefix-less visit from a new browser. `PUT /api/me/locale` mirrors `PUT /api/me/theme` end to end.

**Server-side, messages are codes, not prose.** Every `ApiFailure` carries a `MessageRef` (a catalog key plus positional arguments) alongside an English `message`, and the browser words it — `EndpointClient.toApiError` resolves it at the seam, so pages still just render `err.message` and know nothing about i18n. This is what keeps `ApiFailures`' mappers free of a `Locale` parameter: **no signature in `backend/http/ApiFailures.scala` takes a locale, and none should.** The English text alongside each key is a fallback for callers with no catalog (a `curl`, the OpenAPI examples) and is never what the SPA shows.

`shared/validation/Validation.scala` fails with `MessageRef` for the same reason — it runs on both platforms, so a form and the endpoint behind it now produce identical messages by construction. `validateNonBlank` takes a **catalog key** for the field label rather than the label itself, passed through as a `MessageRef.keyArg` (an `@`-prefixed argument the resolver translates before substituting). That incidentally fixed a real divergence: `GroupsPage` said "Group name" where `GroupService` said "Name" for the same input.

**The catalogs are one JSON file per language, and there is exactly one copy of each.** `web/public/locales/messages.{en,hu}.json` — Vite serves them in dev and nginx out of the built image, both with no configuration, and the backend reads *the same files* off its classpath via one `Compile / unmanagedResourceDirectories` line in `build.sbt`. That reach across module boundaries is deliberate: a translator edits one file per language and there is no generated duplicate to go stale. It works in Docker because the `base` stage does `COPY . .`.

The backend loads them at boot (`backend/i18n/Messages.scala`, `Messages.live`) and **fails the boot if one is missing or malformed**, like the Flyway migration — a deployment whose Hungarian catalog did not make it into the image should not discover that one email at a time. The server renders nothing else from them: the two email templates are its only use, which is the whole reason it holds a catalog at all.

**JSON was chosen over a typed Scala trait so translators need not touch Scala, and the cost of that is that missing keys are runtime bugs.** `MessagesSpec` buys the guarantee back and is what makes the choice safe: it asserts the locales define *identical* key sets, that every `MessageKeys` constant (i.e. every key the server can mint) and every `UiKeys` constant (every key a page renders) exists in all of them, that no unregistered `ui.` key is left lying in a catalog, that a key's `{0}`/`{1}` placeholders agree across locales, and that `.one`/`.other` plural pairs are complete. `MessageKeys` registers each constant as it is declared rather than re-listing them in `all`, since a hand-maintained list is exactly what goes stale and takes the guarantee with it.

Two things Hungarian breaks that English hid:

- **The `"(s)"` idiom** (`s"$n session(s)"`, `"entr(ies)"`, `"day(s)"`) has no Hungarian equivalent — a numeral is followed by the singular, always. Use `MessageCatalog.plural` with a `.one`/`.other` key pair; the selection is a per-language match, not a CLDR rule, and adding a language forces it to be extended.
- **The definite article alternates `a`/`az`** by the following sound, and no placeholder can carry that. So do not compose a Hungarian sentence around an interpolated noun — phrase the frame to sidestep it (`"Kötelező mező: {0}"`, not `"A(z) {0} megadása kötelező"`), or keep the whole sentence as its own key.

`RouteSupport.RequestContext` gained `locale`, read from an `X-Locale` header the generated client sends on every call (falling back to `Accept-Language`, then `en`). It sits there rather than in the endpoint descriptions for the same reason the client address does — it is a property of the request, not of any one operation — and describing it would mean a header codec on every endpoint that might send mail, kept in step by hand. The OAuth `/start` route is the exception: it is reached by the document navigating, so it carries no client headers and takes `?locale=` instead, which the server tucks into the `oauth_state` cookie so it survives the round trip through the provider.

**Page copy goes through `shared/i18n/UiKeys.scala`, the sibling of `MessageKeys`.** The split between the two objects is *who mints the message*, not who renders it: a `MessageKeys` entry is chosen by the server, a `UiKeys` entry is copy a Laminar element renders, and every one of the latter is namespaced `ui.` so the halves stay distinguishable in the catalog. It lives in `shared` rather than in the frontend purely so `MessagesSpec` — which runs on the JVM — can walk `UiKeys.all` the same way it walks `MessageKeys.all`; without that the ~270 keys of page copy would be guarded only by `I18n.t`'s console warning. `MessagesSpec` checks the `ui.` namespace in *both* directions, since an orphaned `ui.` key in the catalogs is copy nothing renders any more (the server's half gets no such check — a `curl` and the OpenAPI examples read it too). A plural constant registers its `.one`/`.other` pair and holds the base, because the base is never a catalog key itself.

Four things that follow from it:

- **Field labels are not duplicated.** A form input whose label already exists as a `MessageKeys` constant — `field.email`, `field.password`, `field.source`, `field.target` — renders that one. Those keys exist precisely so a form and the endpoint behind it cannot disagree about what an input is called.
- **Only labels are translated, never values.** `components/Labels.scala` words `GroupRole`, `TodoStatus`, `login_attempts.outcome` and `audit_log.action`; wherever one sits in a `<select>`, the `option`'s `value` stays the enum's `toString` or the stored code, which is what `controlled(...)` round-trips and what the API is sent. The two stored-code helpers key off the string via `I18n.get` and fall back to the code itself, so a row written by a newer build still renders — the rule the old `LoginOutcome.display` followed.
- **`Formats` follows the page's language, not the browser's.** `dateTime`/`date` pass `I18n.locale.code` as the locale tag through a small `LocalizedDate` facade, because the Scala.js `js.Date` facade declares only the no-argument forms. The *timezone* still comes from the browser, which is the half that matters for "when did this happen relative to when the user says it did".
- Brand and language names stay untranslated by design: `OAuthProvider.displayName`, `Locale.displayName` (the endonym rule — "Magyar" is never "Hungarian"), and the `webapp1` wordmark.

The frontend specs assert on message *keys* rather than copy — with no catalog loaded under jsdom a message resolves to its own key, which is the stronger statement anyway: it says the page routed the right message to the right place, and `MessagesSpec` separately proves that key has real copy behind it. **The English copy is what `e2e/` matches on**, though: that suite runs under `/en/` and finds buttons, headings and placeholders by their text, so changing an English string in `messages.en.json` is a change to the e2e suite's fixtures.

`e2e/tests/translation.spec.ts` is the only place a real catalog is ever rendered, which makes it the only check that can see a key `MessagesSpec` cannot — one no `UiKeys` constant registers, or one assembled by concatenation. It walks every route under both prefixes and fails on either symptom: a `ui.…` key rendered as its own name, or an `i18n: no '…'` console line (which is what catches the keys no page *text* would show — an `aria-label`, a `placeholder`, a `confirm()` string).

### Frontend routing/auth

`AppRouter.Page` is the route ADT (locale-free — the language prefix is Waypoint `basePath`, see **Internationalization**; the two admin listings do carry their query state, see **Paged, sorted and filtered listings**); `Page.guardFor(page)` returns one of `RequireAuth` / `RequireAnon` / `Public`, and `App.renderFor` in `App.scala` is the single place that redirects based on it plus the loaded session state — individual pages don't guard themselves. Admin pages additionally check `user.isAdmin` inline (in `App.renderPage`, or in the `SplitRender` guard for the two listings), falling back to `ForbiddenPage`, since that's not expressible in the guard enum. Pages render through `components/AppShell`, which owns the navbar, theme control, and logout. It has two shapes: `AppShell.render(active, content)` is the authenticated one, and `AppShell.renderPublic(content)` is what sign-in and sign-up use — the same bar minus everything needing a session (nav links, avatar, account menu), with the content centred rather than stacked under the navbar. That is why those pages carry no language picker or theme toggle of their own; the shell's navbar is the only place either one lives. Its three dropdowns (nav menu, account menu, language picker) share `components/Popover`: the popover-API attributes Laminar 17 has no keys for, the unique `id`/anchor-name pair each instance needs, and the feature-checked `hidePopover`.

**The nav is built twice and shown once.** Below `lg` it is a hamburger popover in `navbar-start`; at `lg` and up it is a row of buttons in `navbar-center`, and the breakpoint utilities (`lg:hidden` / `hidden lg:flex`) pick between them. Two things follow. A Laminar element belongs to one place in the DOM, so the two renderings are separate elements built by separate helpers (`navLinks` returns buttons, `navMenuItems` returns `menu` items) — reusing one value would move it, not copy it. And `hidden` is `display:none`, which takes an element out of the accessibility tree, so the *hidden* copy is invisible to `getByRole` as well as to a reader — that is what keeps `e2e/`'s `getByRole('link', { name: 'Groups' })` unambiguous at the suite's desktop viewport rather than a strict-mode violation over two matches. `lg:hidden` sits on the popover as well as on its trigger, because an author `display:none` outranks the display the browser applies to an open popover; without it a menu opened on a phone and then widened would float over the centred nav. The three single-icon controls (language, theme, account) stay in `navbar-end` at every width and fold into nothing.

**The theme control works signed out, and that is why `AppState` owns the theme rather than deriving it from the user.** `AppState.themeSignal` is a `Var` seeded from `localStorage` and rewritten by `setUser`; signed in, a toggle still goes to the server first and only `setUser` moves it (so a failed `PUT /api/me/theme` leaves the old theme standing, as before), while signed out it is a local write. `Main` calls `AppState.initTheme()` before the first render so a dark-theme visitor gets no flash of light while `/api/me` is in flight.

`components/OAuthButtons` renders the provider buttons on `SignInPage`/`SignUpPage` (login) and `SettingsPage` (link). They are plain `a(href := …)` anchors, never `ApiClient` calls: the flow is a chain of top-level redirects, so the document has to navigate — which is also why `ApiClient.oauthStartUrl` is the one place in the frontend that spells out an API path. `OAuthMessages` holds the copy for the `?error=` / `?linked=` codes the callback redirects with, read off `location.search` because the callback lands as a full page load rather than a Waypoint navigation. The redirect targets (`/sign-in`, `/settings`) must stay in step with `AppRouter`'s patterns.

`ApiClient`/`AdminApiClient` are generated from the endpoint descriptions (see the backend section) and expose one named method per endpoint, all returning `EventStream[Either[ApiError, A]]` (per the laminar skill's explicit-flattening convention) rather than throwing. `EndpointClient.run` is the single seam between the two effect systems: it hands the ZIO effect to the runtime, maps the declared failure (each endpoint's own union of `ApiFailure` cases; `run` widens to `ApiFailure`, which works because `ZIO`'s error channel is covariant) to the page-facing `ApiError`, and flattens anything else — a defect, a dead socket, an undeclared status — into the same `ApiError` with status `0`. A failure is therefore always a value on the success path, so `onMountCallback`-driven loads never hang on a rejected promise. DTOs are the `shared` module's case classes, used verbatim on both sides.

**Laminar version note**: `.split` is deprecated in the pinned Laminar version in favor of `.splitSeq` (takes a `StrictSignal` with public `.now()`/`.key` instead of `(key, initial, signal)`) — this contradicts some external Laminar docs/examples; follow the existing `splitSeq` usages in `pages/*.scala` instead.
